token-guard · Validação de Arquitetura Hook efêmero por chamada → Daemon ÚNICO GLOBAL por máquina (nasce/morre com o Windows)

Tese final: na máquina corporativa (VPN + AV Windows + AV empresa + validador de processo + auditoria), cada spawn dispara análise completa do EDR, sem cache. São 300–400 spawns/dia = 300–400 análises individuais que travam execução. Sob burst (60+ req simultâneos de 8 sessões + subagentes), o throughput satura em ~128 req/s e a mediana vai de 53 ms → 263 ms → timeouts de 5–15 s no harness. 1 · Por que "por sessão" está errado — o daemon é GLOBAL

Correção de escopo (do dono): o hook Stop dispara a CADA turno do agente, não no fim da sessão. Então NÃO dá pra matar o daemon no Stop — ele morreria entre uma fala e outra. O modelo certo é: um daemon por máquina, singleton global. Nasce no logon do Windows, atende todas as IDEs e sessões, e morre só no shutdown. Isso elimina de vez o problema de zumbi órfão (ele é esperado ficar rodando) e transforma o pico de RAM em um custo FIXO de ~40 MB.

  • Zero cold-start sob concorrência: os 31 ms de piso somem POR COMPLETO — não há mais N processos disputando criação. Resta IPC local (~0,1–0,5 ms) sobre o mesmo heap aquecido.
  • Throughput ilimitado pelo gargalo de spawn: o nó de ~128 req/s era o teto de CRIAR processos. Um daemon só despacha frames — escala com o event loop do Node (milhares de conexões leves).

  • Serve TODAS as IDEs de uma vez: Copilot CLI, Claude Code, Cursor compartilham o mesmo daemon global — instalei token-guard, o daemon nasce com o Windows e ninguém mais paga spawn.
  • Reúso total do núcleo: o daemon chama o MESMO lib/decide.cjs. Só troca o envelope stdin/stdout por frames JSON-RPC com requestId (o parser do mcp-server.cjs já resolve multiplexação).

5 · Capacidade: quantas requisições o daemon aguenta?

A pergunta central: um único processo Node segura dezenas/centenas de clientes concorrentes? Resposta curta — sim, com folga, porque a decisão é síncrona e leve (~22 ms de lógica pura, sem I/O bloqueante no caminho quente).

7 · Pontos de atenção (viabilidade real)

  • Instalação como serviço de logon: precisa registrar o start no boot do Windows (Run key / Task Scheduler at logon / startup). No POSIX: systemd-user / launchd. É o mecanismo que garante "nasce com o Windows".
  • Singleton robusto: lock por SID (named pipe no Win / socket UNIX path hash no POSIX). Segundo start detecta "já existe" e vira cliente. Self-heal: se o pipe some (crash), o próximo cliente reassume o daemon.
  • Segurança local (ACL): named pipe restrito ao usuário (PIPE_REJECT_REMOTE_CLIENTS + DACL do SID), senão qualquer processo da conta injeta payloads falsos no guard.
  • Stale code no upgrade: handshake de versão no connect; mismatch ⇒ derruba daemon velho e reassume com o binário novo (importante porque ele fica dias no ar).
  • Burst CPU-bound: 60 decisões simultâneas serializam no event loop (~1,3s no pior caso). Mitigar com cache por path + opcional worker_threads. Ver seção 5.
  • Ganho nulo onde já é plugin: no Copilot CLI o in-process JÁ custa 0,55 ms. O daemon vale para o modo hook (Claude Code / Cursor) e unifica tudo num só processo global.

8 · Arquitetura de segurança (fault tolerance — obrigatória)

O dono exige três garantias além do happy-path. Sem elas o daemon vira ponto único de falha pior que o efêmero:

GarantiaCenárioMecanismo
Start on demandDaemon ainda não subiu (primeiro prompt do dia, ou AV travando o boot)No connect-fail, o PRÓPRIO cliente tenta subir o daemon (spawn 1× com lock), espera o pipe nascer, reconecta. Nunca deixa o hook sem guard.
Self-heal no crashNamed pipe caiu no meio do dia (crash do Node, kill acidental)Cliente detecta EPIPE/EOF → tenta reassumir UMA vez via start-on-demand. O segundo processo a chegar pega o lock e sobe de novo. Análise do AV acontece 1×, não N×.
Disarm em erro críticoTentou subir no próximo prompt e deu erro irrecuperável (binário corrompido, permissão negada pelo AV)Após K falhas consecutivas (ex.: 3), o cliente DESARMA o modo daemon e cai no fallback efêmero atual + loga loudly. Nunca entra em loop infinito de respawn contra o antivírus.

  • Elimina o gargalo do EDR: na máquina corporativa o custo dominante NÃO é o Node cold-start (31 ms) nem a lógica (22 ms) — é a análise INDIVIDUAL de cada processo novo pelo AV da empresa, que não tem cache. 300–400 spawns/dia = 300–400 análises. Um daemon = 1 análise no boot, mais nada o resto do dia.
  • RAM livre é pré-requisito: 16 GB com 1 GB sobrando + disco no limite — os picos de N×M × 40 MB são insustentáveis lá. O daemon fixa o consumo em ~40 MB permanentes.
  • Unifica todos os modos: o que já roda como plugin (Copilot CLI, in-process) continua; o que roda como hook (Claude Code/Cursor) migra para o mesmo daemon global. Uma instalação, um processo residente, todas as IDEs.
  • Burst absorvido sem nova análise: quando 60 hooks disparam juntos, NO EFÊMERO viram 60 processos novos = 60 análises EDR simultâneas travando tudo. NO DAEMON viram 60 frames IPC no MESMO processo já aprovado — nenhuma análise extra.

Viável e de altíssimo retorno. Os dados provam a sua tese: o problema NÃO é a latência de 53 ms isolada — é que sob concorrência real (suas 8 sessões + subagentes ≈ 60+ spawns) a mediana vai a 263 ms e o p95 a 409 ms, saturando o throughput em ~128 req/s e estourando o timeout.
