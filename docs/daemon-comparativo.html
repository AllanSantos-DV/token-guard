O Problema Medido

Cada chamada de ferramenta num hook dispara spawn(node …cjs): lê stdin → decide → escreve stdout → morre. Com múltiplas sessões simultâneas, os spawns se multiplicam e estouram RAM/CPU da máquina corporativa (EDR sem cache escaneia cada processo novo individualmente).

A Solução Proposta

1No SessionStart, sobe UM daemon por máquina (named pipe Win / UNIX socket POSIX). Nasce detached, fica residente até shutdown.

2Todos os hooks (PreToolUse, UserPromptSubmit, PostToolUse) viram clientes finos: conectam no pipe já aberto, mandam payload, recebem veredito warm (~1 ms), desconectam.

3Fault tolerance obrigatória: start-on-demand (cliente sobe daemon se ausente), self-heal (EPIPE → resume 1×), disarm-K=3 (falhou 3× seguidas → volta pro modo efêmero + log alto). Nunca loop infinito contra AV/EDR.

Modelo Atual — Efêmero (N sessões × M calls = N×M processos)

Gargalos identificados

• Cold start: ~31 ms só do Node floor em Windows corporativo (sem contar EDR scan).

• Multiplicação de RAM: cada spawn pica ~40 MB; 6 sessões × 8 calls = 48 processos simultâneos possíveis → ~1.9 GB de picos concorrentes numa máquina com ~1 GB livre.

• EDR no-cache: cada processo novo é escaneado individualmente pelo antivírus corporativo. 300–400 spawns/dia = 300–400 scans bloqueantes.

• Timeout cascade: quando a memória satura, os spawns ficam travados → hooks excedem o timeout de 10 s do harness → tela vermelha inteira.

Modelo Proposto — Daemon Único (1 processo + N clientes finos)

Como resolve

• Zero cold start: daemon nasce uma vez no logon; lazy-requires de config/rules ficam quentes na heap residente.

• RAM fixa: ~40 MB total independentemente de quantas sessões chamam. Clientes finos são threads leves do próprio harness, não processos novos.

• EDR 1× só: um único processo escaneado no boot. As conexões ao named pipe não disparam scan novo.

• Cache de decisão: chave {root, ruleSetHash, payload} colapsa repetições a ~0 ms. Mudança de config no disco gera hash diferente → miss automático (invalidação implícita).

• Fallback transparente: se o daemon estiver fora, o cliente tenta subir 1×; se falhar 3× consecutivas, cai pro modo efêmero atual sem quebrar nada. Fail-open preservado.
